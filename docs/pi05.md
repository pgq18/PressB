# LeRobot π₀.₅ in PressB

The `pi05` model plugin uses a [pinned LeRobot revision](https://github.com/huggingface/lerobot/commit/d324ffe810d17264a0b1e628698aa1fa09aa639c)
for the policy, flow-matching training objective, and input/output processors.
PressB supplies the LeRobot dataset training entry point and the schema-v2
inference adapter. [Upstream model documentation](https://huggingface.co/docs/lerobot/en/pi05)

## Environment

Use the existing PressB Python 3.10 or 3.11 environment with a PyTorch build
for your GPU. The installer uses Transformers 5.3.0. It makes Rerun and
W&B optional and accepts Isaac Sim's Packaging version. The upstream model,
processor and dataset code is unchanged.

```bash
python scripts/install_pi05.py
```

Download [the official base weights](https://huggingface.co/lerobot/pi05_base)
and set `policy.pretrained_path` to their local directory. Set
`tokenizer_path` to a local Hugging Face-compatible PaliGemma tokenizer, or
omit the field to use the upstream default with access to the gated
PaliGemma repository.
The tokenizer used during training is saved with the checkpoint.

## Supervised training

Start with [the Cube Stack configuration](../configs/model_training/pi05_cube_stack.yaml).
Edit the local paths, CUDA device, and training budget. The dataset is
LeRobot v3. The example trains the action expert with both cameras and seven
joint/gripper coordinates. The split is by episode. Training uses the shared
PressB image augmentation preset. Validation uses the original frames.

```bash
pressb-model-train --model pi05 --config configs/model_training/pi05_cube_stack.yaml
```

Use `-- --prepare-only` to check the dataset, split, and normalization before
loading the model. For multi-GPU training, launch the same entry point with
`torchrun --standalone --nproc-per-node=2 scripts/train_model.py --model pi05 --config …`.
The batch size is per device. `gradient_accumulation_steps` defaults to 1;
the effective batch is `batch_size × device_count × gradient_accumulation_steps`.
`steps` counts optimizer updates, including when accumulation is enabled.
Use `drop_last: true` for a constant effective batch. Logs record both the
configured batch size and the actual number of samples used by each update.
Rank 0 evaluates and exports model-only checkpoints,
keeping the two latest generations and the best validation checkpoint by default.

### Ascend NPU

See the [Ascend 910C deployment guide](ascend_pi05.md) for the validated conda
environment, pinned input downloads, six-device chunk-16 configurations and
runtime validation evidence.

Use a separate conda environment with a CANN-compatible PyTorch / `torch_npu`
pair and source the server's existing CANN environment script. Set
`policy.device: npu:0`; `torchrun` then selects HCCL and maps each local rank
to a visible NPU. For example, six devices with per-device batch 24 and
one accumulation step produce an effective batch of 144:

```bash
ASCEND_RT_VISIBLE_DEVICES=2,3,4,5,6,7 \
  torchrun --standalone --nproc-per-node=6 scripts/train_model.py \
  --model pi05 --config /path/to/npu-training.yaml
```

The adapter uses native NPU tensors and a model-local FP32 timestep embedding
because Ascend does not support the upstream FP64 embedding calculation.
CUDA and CPU retain their existing implementation. Checkpoint parameter names
and processor formats are unchanged, and saved NPU configurations can be loaded
on CUDA or CPU by overriding the device. Validate a real forward/backward update
and multi-device communication on the installed runtime before a long run.

On ARM hosts, shared CPU sharpness augmentation temporarily uses the native
PyTorch convolution instead of oneDNN, whose grouped-convolution JIT can fail
with `label is too far` in DataLoader workers. The sampled augmentation factor
and torchvision operation are preserved; other transforms and device paths are
unchanged. Validation still uses no random image augmentation.

Set `policy.chunk_size`, `policy.n_action_steps`, and any
`pressb.action.horizon` consistently when changing the action window. The data
loader derives action timestamps from the configured policy chunk size.

The example dataset stores angles in degrees and full gripper width in
centimetres. The simulation interface uses radians and metres. The `pressb`
section describes the camera mapping and both unit conversions. These fields
are persisted in `pressb_pi05.json` alongside the native LeRobot checkpoint and
the saved normalization processors. Point the inference plugin to the
checkpoint's `pretrained_model` directory.

## Simulation evaluation

Set `model.config.checkpoint` in the experiment to the trained
`pretrained_model` directory when using a custom output path.

```bash
pressb inference --config configs/experiments/cube_stack_pi05_eval.json
```

In separate terminals, run
`pressb simulation --config configs/experiments/cube_stack_pi05_eval.json`
in the Isaac environment and
`pressb eval --config configs/experiments/cube_stack_pi05_eval.json`
in the runner environment. The example executes seven actions at 30 Hz.
Adjust the task and runner horizon to fit your checkpoint.
The example uses PressB's HTTP transport in the shared Isaac Sim environment.

For another native LeRobot π₀.₅ checkpoint, supply its local directory with
the saved pre/post processors. Set `model.config.io` to the camera, state,
action and unit mapping when the checkpoint has no PressB sidecar.

## Evaluation performance

The evaluation launcher supports `--performance-profile fast` and two independent
simulators sharing one model service. `--num-envs 8` means eight environments per
simulator; the default profile remains `legacy`. See
[evaluation performance](evaluation_performance.md) for dataset/scene selection,
launch commands, episode and seed semantics, timing interpretation, and the
measured batch-size comparison.
